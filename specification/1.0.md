# RPKG 1.0

## What is RPKG?

RPKG is a simple file format for sharing AI roleplay content. An RPKG file is a ZIP archive with the `.rpkg` extension. Its MIME type is `application/vnd.rpkg`.

An RPKG can contain characters, lorebooks, and other kinds of content that may be added later.

## Package layout

Every package contains these files at its top level:

```text
mimetype
manifest.json
```

Packages can also contain collection folders. RPKG 1.0 defines these folders:

```text
characters/<id>.json
lore/<id>.json
```

The folder names show what kinds of content are in the package. Apps should look through the top-level folders to find content. The manifest does not need to repeat that list.

`mimetype` contains `application/vnd.rpkg` as UTF-8 text. Writers should store it without ZIP compression or a trailing newline. Readers should still accept one trailing line break.

`manifest.json` and all collection documents use UTF-8 JSON.

Use forward slashes in archive paths. Paths must stay inside the package. Do not use absolute paths, `.` segments, or `..` segments.

An app should reject a package if it is not a ZIP file, does not have `manifest.json`, or has an invalid manifest. It should also reject duplicate paths and paths that would conflict on a case-insensitive file system.

## Manifest

The manifest follows `schemas/1.0/manifest.schema.json`.

```json
{
  "version": "1.0",
  "exportedAt": "2026-08-11T12:00:00.000Z"
}
```

`version` is the RPKG format version. It uses `major.minor` form. Apps should reject a package with a newer major version that they do not support. They can often read a newer minor version by ignoring fields they do not know.

`exportedAt` is the time the package was created. It uses the usual ISO 8601 date-time format and is required.

`generator` is optional. It can name the app and app version that created the package.

## Collections and documents

Each item is one JSON file directly inside its collection folder. Its file name is `<id>.json`, and that ID must match the document's `id` field.

IDs are 8 to 128 characters long. They can use letters, numbers, underscores, and hyphens.

Each item keeps its own supporting data. For example, a character avatar or an image pack can live inside that character's JSON document as a data URL. This keeps a single item easy to copy, move, edit, and import.

Apps should ignore collection folders and files they do not understand. When possible, they should also keep unknown JSON fields when they read and write a known document.

### Shared metadata

Character and lorebook documents can include a `metadata` object. It can include an author, source, license, language, dates, tags, and content warnings. The schema lists the available fields.

Metadata is helpful context. Apps should not treat it as proof that a claim is true.

### Characters

Character documents live in `characters/`. They follow `schemas/1.0/character.schema.json`.

`definition` holds the roleplay definition or prompt text. `greetings` holds zero or more opening messages. `avatar` is either `null` or a data URL.

### Lorebooks

Lorebook documents live in `lore/`. They follow `schemas/1.0/lorebook.schema.json`.

Each lorebook entry has an ID, name, and content. Apps can add extra fields for their own lorebook features.

## Extensions

Apps can add fields to JSON documents. Other apps should ignore fields they do not understand.

Apps can also add their own collection folders. To avoid naming conflicts, use a reverse-domain-style name for non-standard folders, such as `com.example.voice-pack`.

## Safe handling

Treat RPKG files as files from outside your app. Do not write package files outside the folder chosen by the user. Do not run anything from a package.

Apps should set reasonable limits for ZIP file size, number of files, unpacked size, compression ratio, JSON nesting, and data URL size. We will add suggested limits in a later version of this documentation.
